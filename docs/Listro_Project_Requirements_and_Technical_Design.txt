====================================================================== 1.
PROJECT OVERVIEW
======================================================================

1.1 Project name Listro

1.2 Product concept Listro is a shoe-cleaning and shoe-care service
platform. Customers request shoe-cleaning services through a mobile
application. Listro arranges collection of the shoes, transports them to
a washing/cleaning center, processes them, and returns the cleaned shoes
to the customer.

The platform coordinates customers, delivery personnel, cleaning-center
operators, managers, and administrators. It provides order management,
service selection, pickup and return delivery, shoe inspection, cleaning
workflow tracking, payment recording, notifications, reporting, and
operational administration.

1.3 Main business objective Build a reliable, maintainable, secure, and
scalable digital platform that makes it easy for customers to request
shoe cleaning and gives Listro staff clear visibility and control over
every order from placement to delivery.

1.4 Product goals - Make ordering shoe-cleaning services simple for
customers. - Support pickup from the customer’s address and return
delivery. - Track every order through clearly defined operational
stages. - Record the condition of shoes before cleaning and, where
appropriate, after cleaning. - Assign delivery and cleaning tasks to
responsible employees. - Support cash and online payment methods. - Give
managers operational dashboards and reports. - Give administrators
control over users, roles, services, branches, and system settings. -
Preserve a reliable history of order status changes and employee
actions. - Allow the business to start with one cleaning center while
supporting multiple branches in the future.

1.5 Initial scope The initial release is intended for one operating
cleaning center. The database and backend should be designed so
additional branches can be introduced later without rebuilding the core
system.

The project is a modular monolith initially, not a microservices system.
This keeps development and deployment manageable while maintaining clear
module boundaries.

2. USERS, ROLES, AND RESPONSIBILITIES
======================================================================

2.1 Customer The customer uses the Flutter mobile application to: -
Register and sign in. - Manage their profile and contact details. - Add,
edit, and select pickup/return addresses. - Browse available
shoe-cleaning services and prices. - Add one or more pairs of shoes to
an order. - Select a service for each pair. - Provide shoe details and
special instructions. - Select a preferred pickup date/time, subject to
availability. - Review the order and estimated total. - Submit an
order. - View order details and current status. - Follow pickup,
cleaning, and return-delivery progress. - Receive order and payment
notifications. - View payment status and order history. - Contact Listro
support through the channels provided by the business. - Cancel an order
when the cancellation policy and current order state allow it. - Submit
feedback or a rating if this feature is enabled.

2.2 Delivery personnel Delivery personnel use the Flutter mobile
application to: - Sign in with an employee account. - View deliveries
assigned to them. - View the delivery type: customer pickup or return
delivery. - View the customer name, contact information, address, and
relevant instructions. - View navigation/location information when a
maps integration is enabled. - Accept or acknowledge an assignment if
the business workflow requires it. - Update delivery progress. - Confirm
that shoes were collected from the customer. - Record a failed pickup or
delivery with a reason. - Confirm handover of shoes to the cleaning
center. - Receive return-delivery assignments after cleaning is
complete. - Confirm that cleaned shoes were returned to the customer. -
View their own completed and active assignments.

The system should record who performed each delivery action and when it
occurred. Employee location should only be collected when necessary for
an active work task and in accordance with the business privacy policy.
The system must not track employees outside their work assignments.

2.3 Operator Operators use the Flutter mobile application to: - Sign in
with an operator account. - View shoes/orders received at the cleaning
center. - Confirm physical receipt of shoes. - Review customer-provided
notes and delivery information. - Perform and record a shoe condition
inspection. - Capture before-cleaning photos where supported. - Record
existing damage, stains, missing accessories, or other relevant
observations. - View the cleaning service selected for each pair. -
Start and update cleaning tasks. - Record operational notes or issues. -
Mark cleaning as completed. - Capture after-cleaning photos where
supported. - Mark shoes as ready for return delivery. - Hand shoes over
to delivery personnel and record the handover.

2.4 Manager Managers can use the Flutter mobile application and the
Next.js web management dashboard.

Manager capabilities: - View the operational dashboard. - View and
manage orders for authorized branches. - Confirm or reject orders
according to business policy. - Assign and reassign delivery
personnel. - Assign cleaning tasks to operators. - Monitor pickup,
cleaning, and return-delivery progress. - Review shoe inspection records
and operational exceptions. - Manage daily workload and employee
assignments. - View customers and relevant customer order history. -
Review payments and payment exceptions. - Manage service availability
and pricing where permitted. - View operational reports. - Handle
cancellations, failed deliveries, complaints, and order issues. -
Monitor employee activity and workload. - View audit history relevant to
their permissions.

Managers must not automatically receive every administrator permission.
Their access should be limited by role and branch assignment.

2.5 Administrator / Owner Administrators have the highest level of
system access. They can use the Flutter mobile application and the
Next.js web management dashboard.

Administrator capabilities: - Manage users and employee accounts. -
Assign roles and permissions. - Activate, deactivate, or suspend
accounts. - Manage branches and branch details. - Manage services,
service descriptions, prices, and availability. - Configure business
settings and operating rules. - View and manage all orders. - View and
manage customers and employees. - Review all payment records and payment
exceptions. - View business-wide reports and analytics. - Review audit
logs. - Configure notification and integration settings. - Manage
system-level settings and access policies.

High-impact actions should be permission-controlled and recorded in the
audit log.

2.6 Support role A dedicated support role is not mandatory for the first
release. If introduced, it should have restricted access to customer
inquiries, order details, and support actions without receiving
financial or system-administration permissions by default.

3. TARGET APPLICATIONS AND PLATFORMS
======================================================================

3.1 Mobile application One Flutter application for Android and iOS.

The same mobile application supports role-based experiences for: -
Customer - Delivery personnel - Operator - Manager - Administrator

After login, the backend-provided role and permissions determine which
screens and actions are available. Hiding a button in the app is not
sufficient security; the backend must enforce authorization on every
protected operation.

3.2 Web management dashboard A Next.js web application for: - Manager -
Administrator / Owner

The web dashboard provides larger-screen workflows for order management,
employee management, services, branches, reports, and administration.

3.3 Backend API A NestJS REST API provides shared business logic and
data access for both mobile and web applications.

3.4 Initial deployment model - Flutter mobile clients communicate with
the hosted API over HTTPS. - Next.js dashboard communicates with the
same API. - NestJS communicates with PostgreSQL and Redis. - Background
workers process queued jobs. - Object storage stores photos and other
uploaded files. - Push notifications are delivered through Firebase
Cloud Messaging.

4. TECHNOLOGY STACK
======================================================================

4.1 Mobile application Framework: Flutter Language: Dart

Recommended supporting technologies: - Riverpod: application state
management and dependency injection. - GoRouter: navigation and route
protection. - Dio: HTTP client for API requests, interceptors, and error
handling. - Drift with SQLite: local database and selected offline
capabilities. - Flutter Secure Storage: secure storage for
authentication tokens. - Firebase Cloud Messaging: push notifications. -
Google Maps or Mapbox: maps, address selection, and delivery
navigation. - Image picker / camera packages: shoe inspection and order
photos. - Flutter test: unit, widget, and integration testing.

4.2 Backend Framework: NestJS Language: TypeScript Architecture: Modular
monolith using feature modules.

Recommended modules: - Authentication - Users - Customers - Employees -
Roles and permissions - Branches - Addresses - Shoes - Services -
Orders - Deliveries - Washing / cleaning tasks - Shoe inspections -
Payments - Notifications - Reports - Audit logs - File uploads - Health
checks

4.3 Database Database: PostgreSQL ORM: Prisma ORM 7.10.1

PostgreSQL is the authoritative persistent data store. Prisma provides
schema management, type-safe database access, and migrations.

The initial schema supports one active center while allowing multiple
branches in the future.

4.4 Cache and background jobs Redis: - Cache frequently requested data
where appropriate. - Store short-lived operational data where
appropriate. - Support background job infrastructure.

BullMQ: - Process background jobs such as notification delivery,
email/SMS tasks, report generation, and other work that should not block
API requests. - Implement retries and failed-job handling. - Jobs must
be safe to retry and should avoid duplicate business effects.

4.5 Web dashboard Framework: Next.js Language: TypeScript

Recommended supporting technologies: - React - A consistent component
library such as shadcn/ui - A form library and schema validation
library - TanStack Query or an equivalent server-state approach where
useful - Responsive layouts and accessible components

The dashboard must use the backend API rather than directly accessing
the database.

4.6 Authentication and security - Short-lived JWT access tokens. -
Rotating refresh tokens with server-side revocation support. - Argon2id
for password hashing. - Flutter Secure Storage for mobile token
storage. - Secure, HttpOnly cookies for web refresh-token handling where
appropriate. - Role-based access control (RBAC). - Permission checks in
NestJS guards and service methods. - Rate limiting for sensitive
endpoints. - Validation of all incoming request data. - HTTPS in
production.

4.7 File storage Use S3-compatible object storage for: - Shoe
before/after photos. - Inspection photos. - Optional customer
attachments. - Other business documents if required.

Store file metadata and object keys in PostgreSQL, not large binary
files. Use private storage by default and short-lived signed URLs for
authorized access.

4.8 Maps and location Google Maps or Mapbox may be used for: - Address
search and selection. - Map display. - Delivery route assistance. -
Optional active-delivery location sharing.

The provider and pricing must be evaluated before production selection.
Do not collect more location data than the delivery workflow requires.

4.9 Notifications Firebase Cloud Messaging for mobile push
notifications.

The backend should create notification records and dispatch messages
through background jobs. Push delivery is not guaranteed, so important
order updates must also be visible in the application.

Other channels, such as SMS or email, may be added after selecting
providers and reviewing cost and local availability.

4.10 Monitoring and deployment - Docker and Docker Compose for local
infrastructure and repeatable environments. - Git and GitHub for source
control. - GitHub Actions for automated checks and deployment
workflows. - Sentry or an equivalent service for error monitoring. -
Structured application logs. - Database backups and restore
procedures. - Separate development, staging, and production
environments.

5.1 Architecture overview

<——> Next.js Management Dashboard | +—— PostgreSQL (Prisma ORM) | +——
Redis | | | +—— BullMQ background jobs | +—— Object Storage | +——
Firebase Cloud Messaging | +—— Maps provider (when enabled)

5.2 Architectural principles - Modular monolith for the initial
release. - Clear separation between controllers, services, data access,
and domain rules. - Shared backend business rules for mobile and web
clients. - PostgreSQL as the source of truth. - Backend-authoritative
order status and payment status. - Explicit authorization for every
protected operation. - Transactional database updates for operations
that must succeed together. - Background jobs for slow or retryable
work. - API versioning for future compatibility. - Avoid premature
microservices. - Keep external integrations behind service abstractions
so providers can be changed later.

FR-CUST-03: Customers must be able to edit and delete their saved

FR-SVC-05: Service availability may differ by branch. FR-SVC-06: The

7. ORDER LIFECYCLE AND BUSINESS RULES
======================================================================

7.1 Proposed main order statuses

1.  PLACED Customer submitted the order.

2.  CONFIRMED The order was accepted by the business.

3.  DELIVERY_ASSIGNED A pickup delivery person has been assigned.

4.  PICKUP_IN_PROGRESS The delivery person is handling the pickup.

5.  RECEIVED_AT_CENTER The cleaning center confirmed physical receipt of
    the shoes.

6.  WASHING_IN_PROGRESS Cleaning work has started.

7.  WASHING_COMPLETED Required cleaning work has been completed.

8.  READY_FOR_DELIVERY Shoes are ready and waiting for return delivery.

9.  OUT_FOR_DELIVERY The return delivery is in progress.

10. DELIVERED Shoes have been handed back successfully.

11. CANCELLED The order was cancelled according to policy or by an
    authorized exception.

12. REJECTED The business declined the order and recorded a reason.

7.2 Important business rules - The backend, not the mobile or web
client, controls valid order status transitions. - Every transition must
record who made it and when. - An order can contain multiple pairs of
shoes. - Each pair can have its own cleaning service and price. - Each
order item should have its own inspection and cleaning progress where
operationally necessary. - An order should not become ready for return
until all required items are complete. - A return delivery should not be
completed before the shoes are ready. - A failed pickup or return
delivery must include a reason. - Reassignment must preserve the
previous assignment history. - The order total must be calculated on the
backend. - Historical order prices must not change when a service price
changes. - Payment records must be independent from order records. - An
order can have more than one payment attempt. - An order may be
partially paid if that policy is enabled. - Delivered orders should be
immutable in normal workflows; corrections must use authorized
adjustment actions and audit records. - Do not permanently delete
financial or operational history required for accountability.

7.3 No-show and failed pickup scenario If a delivery person arrives and
the customer is unavailable: - The delivery person records a failed
pickup. - A reason and attempt timestamp are stored. - The manager can
contact the customer and arrange another attempt. - The order remains in
an appropriate pending/exception state. - Any additional delivery fee
must follow a clearly defined business policy. - The system must not
mark the order as received at the center.

7.4 Shoe custody and handover The system should make custody changes
explicit: - Customer to delivery person. - Delivery person to
center/operator. - Operator/center to return delivery person. - Return
delivery person to customer.

Each handover should record the responsible people, timestamp, and
confirmation. This reduces disputes about missing or damaged shoes.

8. DATA MODEL AND DATABASE REQUIREMENTS
======================================================================

8.1 Main database entities

User - id - name/profile fields as appropriate - email and/or phone -
password hash or external identity reference - role - status -
timestamps

Customer - id - user id - customer-specific information - timestamps

Employee - id - user id - employee status - employee details -
timestamps

Branch - id - name - address and contact details - status - timestamps

BranchEmployee - branch id - employee id - branch assignment and role
scope

Address - id - customer id - address details - optional latitude and
longitude - default-address indicator

Shoe - id - customer id where a reusable customer shoe profile is
required - shoe type, brand, color, description, and optional metadata

Service - id - name - description - base price - active status

BranchService - branch id - service id - branch-specific price or
availability where required

Order - id - unique order/booking code - customer id - branch id -
pickup address reference or address snapshot - preferred pickup
schedule - status - subtotal, fees, discounts, tax if applicable,
total - notes - timestamps

OrderItem - id - order id - shoe description or shoe reference - service
reference - service name snapshot - unit price snapshot - quantity if
applicable - item-specific notes - item status where needed

Delivery - id - order id - delivery type (PICKUP or RETURN) - assigned
employee - status - scheduled time - started/completed timestamps -
failure reason - handover/proof details

WashingTask - id - order item id - assigned operator - status -
started/completed timestamps - notes

ShoeInspection - id - order item id - inspecting employee - condition
notes - before/after inspection type - photo references - timestamp

Payment - id - order id - amount - method - status - provider
reference - payment transaction reference - timestamps

OrderStatusHistory - id - order id - previous status - new status -
actor user id - note - timestamp

Notification - id - recipient user id - type - title/body or template
data - read status - related entity reference - dispatch status -
timestamp

AuditLog - id - actor user id - action - entity type and entity id -
metadata - timestamp

8.2 Data design rules - Use UUIDs or Prisma-generated cuid identifiers
consistently. - Use appropriate unique constraints for email, phone
where required, order codes, and provider references. - Use foreign keys
and deliberate deletion rules. - Use Decimal types for money, not
floating-point types. - Store timestamps consistently, preferably in
UTC. - Store business timezone configuration for displaying local
schedules. - Add indexes to frequently filtered fields such as order
status, customer id, assigned employee id, branch id, and timestamps. -
Use database transactions for multi-record business operations. - Use
soft deactivation for users/services where historical records must
remain. - Store immutable price snapshots in order items. - Avoid
storing unnecessary personal data. - Keep payment secrets and passwords
out of ordinary application records.

8.3 Current Prisma schema progress A complete initial Prisma schema has
been created and formatted in apps/api/prisma/schema.prisma. It includes
models for: User, Customer, Employee, Branch, BranchEmployee, Address,
Shoe, Service, BranchService, Order, OrderItem, Delivery, WashingTask,
ShoeInspection, Payment, OrderStatusHistory, Notification, and AuditLog.

The schema includes enums for user roles/statuses, employee and branch
statuses, order statuses, delivery types/statuses, washing statuses,
payment methods, and payment statuses.

The schema was validated and Prisma Client generation succeeded with
Prisma 7.10.1.

The database migration has not yet been confirmed successful. Do not
assume that the database schema has been applied until migration status
and database inspection confirm it.

9. NON-FUNCTIONAL REQUIREMENTS
======================================================================

Non-functional requirements describe how well the system must operate.

9.1 Security - All production network traffic must use HTTPS. -
Passwords must be hashed using Argon2id or a suitably configured modern
password-hashing algorithm. - Access tokens must be short-lived. -
Refresh tokens must rotate and support revocation. - Tokens must not be
stored in insecure plaintext storage on mobile. - Web authentication
cookies must use secure settings appropriate to the deployment. - All
endpoints must validate authentication and authorization. - Role and
branch permissions must be enforced by the backend. - Input must be
validated and sanitized appropriately. - Rate limiting must protect
login, password reset, and other sensitive endpoints. - Secrets must be
stored in environment variables or a managed secrets service. -
Production secrets must never be committed to Git. - File uploads must
validate type, size, and authorization. - Private photos must not be
publicly accessible by default. - Payment verification must happen
server-side. - Audit logs must capture sensitive administrative actions
without recording secrets. - Dependencies must be updated and scanned
regularly. - Administrative accounts should use stronger authentication
controls; multi-factor authentication is recommended.

9.2 Performance Initial targets to validate through testing: - Common
API requests should generally complete within 500 ms under normal
expected load, excluding external providers and large uploads. -
Dashboard lists must use pagination. - Search and filters must be backed
by indexed database queries where appropriate. - Large reports should
use background jobs if they are expensive. - Images should be
resized/compressed where suitable and uploaded directly to object
storage through controlled upload flows. - Avoid unnecessary database
queries and N+1 query patterns. - Use caching only where it does not
create stale or unsafe business data.

9.3 Availability and reliability - Production service should target at
least 99.5% monthly availability initially, with a higher target
considered as the business grows. - Database backups must run on a
defined schedule. - Backup restoration must be tested periodically. -
Background jobs must support retries and failed-job inspection. - API
health checks must report application and dependency health. - Critical
order updates must be persisted before notification dispatch. - The
system must handle temporary mobile network loss gracefully. - Duplicate
requests must not create duplicate orders or payments.

9.4 Scalability - The architecture must support growth in customers,
orders, employees, and branches. - Branch identifiers and authorization
scope must be part of relevant business records. - Stateless API
instances should be possible to scale horizontally. - Redis and BullMQ
should handle asynchronous workloads. - PostgreSQL indexes and query
plans must be reviewed as data grows. - Avoid splitting into
microservices until measurable operational or scaling needs justify it.

9.5 Usability and accessibility - Mobile screens must be responsive to
common Android and iOS screen sizes. - The web dashboard must work on
common desktop and tablet widths. - Use clear status labels and
consistent workflow actions. - Forms must provide understandable
validation messages. - Important destructive actions must require
confirmation. - Provide loading, empty, success, and error states. - Use
accessible color contrast, readable text, and semantic controls. -
Support localization in the architecture; initial language selection
remains a product decision.

9.6 Maintainability - Use TypeScript strict mode in the backend and
dashboard. - Follow consistent naming, formatting, and linting rules. -
Keep modules focused on a business capability. - Separate controllers
from business logic. - Use shared validation schemas/contracts where
practical. - Document environment variables and deployment procedures. -
Add automated tests for business-critical behavior. - Keep architecture
and database documentation current.

9.7 Compatibility - Support currently maintained Android and iOS
versions selected at release time. - Support current major versions of
Chrome, Edge, Firefox, and Safari for the web dashboard. - Define
minimum supported device and browser versions before production
launch. - Test on physical devices as well as emulators.

9.8 Privacy - Collect only information required to provide the
service. - Restrict customer addresses and phone numbers to authorized
staff. - Restrict shoe photos to users who need them for service or
dispute resolution. - Define retention periods for personal data,
photos, and operational records. - Provide a process for customer data
access and correction where legally required. - Do not track delivery
personnel outside active work tasks. - Review applicable Ethiopian
privacy, consumer, tax, and payment requirements before launch.

9.9 Observability - Use structured logs with correlation/request IDs. -
Monitor API errors and latency. - Monitor database connectivity and
resource usage. - Monitor queue depth and failed jobs. - Track key
business metrics such as orders placed, orders delivered, failed
pickups, and payment failures. - Avoid logging passwords, tokens, full
payment credentials, or unnecessary personal data.

11. REAL-TIME AND OFFLINE BEHAVIOR
======================================================================

11.1 Real-time updates Socket.IO may be introduced for live order and
delivery updates where polling or push notifications are insufficient.

Potential events: - order.status.updated - delivery.assigned -
delivery.status.updated - washing_task.assigned -
washing_task.status.updated - notification.created

Every event must be authorized. A user must only receive events for
records they are allowed to access.

11.2 Offline support The mobile application should handle intermittent
connectivity: - Cache selected read-only data. - Show a clear offline
indicator. - Preserve safe, unsent form data where appropriate. - Queue
only operations designed for safe retry. - Revalidate permissions and
business rules on the server when reconnecting. - Do not treat an
offline status update as final until the server confirms it. - Use
idempotency keys to reduce duplicate submissions.

The first release should prioritize reliable online workflows before
implementing complex offline synchronization.

16. RISKS AND MITIGATIONS
======================================================================

Risk: Shoes are lost or confused between orders. Mitigation: - Unique
order and item identifiers. - Labels or QR codes if operationally
useful. - Explicit custody handovers. - Inspection photos and
timestamps. - Employee accountability and audit history.

Risk: Customer disputes about pre-existing damage. Mitigation: -
Before-cleaning inspection. - Photos and notes. - Customer
acknowledgement for exceptional conditions where required.

Risk: Delivery person cannot reach customer. Mitigation: -
Failed-attempt status and reason. - Rescheduling workflow. - Clear
customer communication. - Defined extra-attempt policy.

Risk: Incorrect order pricing. Mitigation: - Backend price
calculation. - Price snapshots on order items. - Decimal money fields. -
Transactional order creation.

Risk: Fake or inconsistent online payment status. Mitigation: -
Server-to-server verification. - Signed webhook validation. - Idempotent
payment processing. - Reconciliation reports.

Risk: Unauthorized access to customer information. Mitigation: - RBAC
and branch scope. - Backend authorization. - Secure file access. - Audit
logs. - Rate limits and security testing.

Risk: Database loss. Mitigation: - Automated backups. - Restore tests. -
Migration review. - Restricted production access.

Risk: Project complexity grows too early. Mitigation: - Modular
monolith. - MVP prioritization. - Add integrations only when business
value is clear.

20. FINAL PROJECT SUMMARY
======================================================================

Listro is a role-based shoe-cleaning service management platform
consisting of:

-   A Flutter mobile application for customers and operational
    employees, with manager and administrator access.
-   A Next.js web dashboard for managers and administrators.
-   A NestJS TypeScript backend that owns business rules and
    authorization.
-   PostgreSQL with Prisma ORM for persistent data.
-   Redis and BullMQ for caching and background processing.
-   Firebase Cloud Messaging for push notifications.
-   S3-compatible object storage for shoe and inspection photos.
-   Google Maps or Mapbox for address and delivery assistance.
-   Docker, GitHub Actions, and monitoring tools for development and
    operations.

The core workflow is: Customer places order -> Manager confirms order ->
Delivery person collects shoes -> Center receives and inspects shoes ->
Operator cleans shoes -> Shoes are marked ready -> Delivery person
returns shoes -> Customer receives shoes -> Payment and order records
are reconciled.

The most important engineering principles are: - Keep the backend
authoritative. - Enforce role and branch permissions on the server. -
Track every important order and custody transition. - Preserve
inspection and payment history. - Use secure authentication and
server-side payment verification. - Build the first release as a modular
monolith. - Test each milestone before proceeding. - Preserve working
features and avoid unnecessary destructive changes.
